### 1.3 Per-class Precision / Recall / F1 (all 15 classes, all 3 models)

`data/cache/metrics/summary.json` only persists **per-class F1** (`per_class_f1`), not
per-class precision or recall — `train.py` computes `per_class_precision`/`per_class_recall`
in memory (via `precision_recall_fscore_support(..., average=None)`) but never writes them to
disk. To answer this item in full, `scripts/report/per_class_metrics_from_cm.py` **derives**
precision/recall/F1 per class directly from the cached confusion-matrix JSON files using the
standard formulas (Precision = diagonal / column-sum, Recall = diagonal / row-sum, F1 =
2PR/(P+R)) — mathematically identical to what `sklearn` computes internally, not a new
methodology. The derived F1 values were cross-checked against `summary.json`'s stored
`per_class_f1` and match to full float precision (e.g. LightGBM BENIGN F1 derived =
0.9986610375140922, stored = 0.9986610375140922 — exact match). Raw output saved at
`scripts/report/out_per_class_metrics.json`. Support = row-sum of the confusion matrix
(count of that class's true instances in the test split).

### 2.6 SMOTE configuration, as coded

From `backend/app/data/loader.py`, function `prepare_data()`:

- **Library/class**: `imblearn.over_sampling.SMOTE`
- **k_neighbors**: `k_neighbors = min(5, min_class_count - 1)`, where `min_class_count` is the
  smallest class count in the pre-SMOTE training split (Heartbleed = 9, so
  `k_neighbors = min(5, 8) = 5` in this actual run). If any class had fewer than 6 samples the
  code would set `k_neighbors = 1` with a logged warning (not triggered this run since the
  smallest class, Heartbleed, has 9 samples).
- **Sampling strategy**: a per-class dict cap, not `"auto"`:
  ```python
  smote_ceiling = 20000
  sampling_strategy = {
      int(label): smote_ceiling
      for label, cnt in zip(unique_labels, count_before)
      if cnt < smote_ceiling
  }
  ```
  i.e. every class already at or above 20,000 samples is left untouched; every class below
  20,000 is oversampled up to exactly 20,000.
- **random_state**: `42`.

**Verbatim code comment explaining why the cap was chosen** (`backend/app/data/loader.py`, immediately above the `smote_ceiling` line):

> ```
> # Cap the oversampling target instead of fully matching the majority class.
> # CIC-IDS-2017's class sizes span ~9 (Heartbleed) to ~1.8M (BENIGN) in the training
> # split -- fully balancing to the majority count (sampling_strategy="auto") forces
> # SMOTE to interpolate the same handful of minority points into hundreds of thousands
> # of near-duplicate synthetic rows (e.g. ~200,000x for Heartbleed). Empirically this
> # extreme duplication destabilizes LightGBM's histogram-based tree growth (training
> # accuracy *drops* as more boosting rounds are added -- a sign of divergence, not
> # underfitting), even though Random Forest/XGBoost tolerate it. Capping the target
> # keeps SMOTE's intended role (give minority classes real gradient signal) without
> # manufacturing a synthetic manifold so dense it destabilizes training.
> ```

### 4.2 Cascade cost saving

| Metric | Value |
|---|---|
| Mean cascade latency per flow | 22.521605683946692 ms (measured over 200,000 flows, same pass as 4.1) |
| Mean latency if all 3 models ran on every flow (brute force, no early exit) | 27.542270680255022 ms (measured over a dedicated 10,000-flow timing pass) |
| **Percentage saving** | **18.23%** |

Method: both figures are real `time.perf_counter()` wall-clock measurements, not calculated
from per-model latency figures. The brute-force path replicates `detect()`'s own preprocessing
(feature-vector construction, `scaler.transform`, `pandas.DataFrame` construction) then calls
all three models' `.predict_proba()` unconditionally with no early exit, so the comparison
isolates the *model-calling* difference the cascade is designed to save, not preprocessing.

**Honest observation**: this 18.23% saving is much smaller than a naive "we skip 2 of 3 models
on 99.7% of flows so should save close to two-thirds of the time" intuition would suggest. The
reason, visible directly in the numbers: single-row inference overhead (Python-level feature
dict construction, `scaler.transform`, `pd.DataFrame` construction — all paid identically by
both paths) dominates the per-flow latency far more than the actual `predict_proba()` model
calls do at this single-row, un-batched call pattern. The cascade's real saving from skipping
Tier 2/3 model calls is present but modest in wall-clock terms *for this specific
single-flow-at-a-time API shape* — it would very likely look larger under a batched/vectorized
calling pattern (where fixed per-call Python overhead is amortized and the model-inference
proportion of total cost rises), but that is a different measurement than what was run here.
This qualifies — but does not remove — the cascade's cost-saving rationale, and is worth
stating plainly rather than only reporting the flattering framing.

**Notable, non-obvious finding, reported plainly**: accuracy *drops* sharply at each escalation

precisely the hardest, most ambiguous slice of traffic (dominated by the weak Web Attack
classes per 4.1). The weighted vote resolves genuine three-way disagreement on hard cases, and
still gets most of them wrong — it is a "best available decision on the hardest residue," not a
higher-accuracy tier than 1/2. This is an important nuance for a report to state explicitly
rather than let a confusion-matrix-only view imply the cascade "gets more accurate as it tries
harder."

### 6.3 SQLite file location and migrations

- Location: `backend/app/config.py` → `DATABASE_URL: str = os.getenv("DATABASE_URL", f"sqlite:///{Path(DATA_CACHE_DIR) / 'app.db'}")`, i.e. **`data/cache/app.db`** by default.
- Table creation: `SQLModel.metadata.create_all(engine)` in `init_db()` (`backend/app/db/session.py`) — creates tables that don't yet exist; **does not alter existing tables**.
- Migration mechanism: **no migration framework** (no Alembic or equivalent) — NOT FOUND.
  Schema evolution on an already-existing SQLite file is handled by hand-written, idempotent
  `ALTER TABLE`/`CREATE INDEX` statements inside `init_db()` itself, guarded by
  `PRAGMA table_info(...)` existence checks (SQLite has no `ADD COLUMN IF NOT EXISTS`). Example,
  verbatim from `backend/app/db/session.py`:
  ```python
  for column in ("timestamp", "predicted_label", "tier", "severity"):
      conn.execute(text(f"CREATE INDEX IF NOT EXISTS ix_alert_{column} ON alert ({column})"))

  existing_cols = {row[1] for row in conn.execute(text("PRAGMA table_info(conversation)")).fetchall()}
  if existing_cols and "pinned" not in existing_cols:
      conn.execute(text("ALTER TABLE conversation ADD COLUMN pinned BOOLEAN DEFAULT 0"))
      conn.execute(text("CREATE INDEX IF NOT EXISTS ix_conversation_pinned ON conversation (pinned)"))
  ```
  Test isolation: `backend/conftest.py` overrides `DATABASE_URL` to a fresh `tempfile.mktemp()`
  SQLite path before the app is imported, so `pytest` never touches the real dev database.

```python
if base == "Info":
    return "Info"          # BENIGN never downgrades
if confidence < 0.70:
    if base == "Critical": return "High"
    elif base == "High":   return "Medium"
    elif base == "Medium": return "Low"
    elif base == "Low":    return "Low"   # floor

```

### 8.3 Synthetic IP/port metadata generation

Function: `get_raw_flow_metadata(idx: int, label: str)`, `backend/app/ml/metadata_helper.py` (full file, 53 lines). Deterministic per-flow via `np.random.default_rng(idx)` (seeded by the row index, so the same `idx` always produces the same synthetic IP/port). Branches by keyword-matching the label: BENIGN → `192.168.10.x` client to Web Server `:80`; DDoS/Hulk/GoldenEye/slowloris/Slowhttptest → `10.0.0.x` external to Web Server `:80`; PortScan → fixed `172.16.0.15` to DB Server, sequential dest port; Brute/Patator → fixed `172.16.0.22` to port 22 (SSH) or 21 (FTP); Sql Injection → fixed `172.16.0.88` to DB Server `:3306`; generic fallback → `172.16.0.x` to Workstation `:8080`.

**Confirmation it runs after classification and feeds nothing into any decision**: in both
call sites —`backend/app/simulator/simulator.py`'s `_runner()` (`result = detector.detect(...)`
is called first; `get_raw_flow_metadata(idx, predicted_label)` is called immediately after,
using the *already-produced* `predicted_label` as an input, purely to pick a plausible-looking
IP range for display) and `backend/app/main.py`'s `/api/predict` (same order: `detector.detect()`
first, then `get_raw_flow_metadata(idx, label)` with the resulting label) — metadata generation
strictly follows classification and is never read back into `CascadeDetector.detect()` or any
model input. It is purely cosmetic, used only for the Attack Map visualization and alert display.

### 8.4 Rare-class round-robin selection logic

`backend/app/simulator/simulator.py`, `_runner()`, function `get_next_low_sample_idx()`:
```python
if self.current_scenario != "mixed_attack" and len(source_indices) < 50:
    idx = get_next_low_sample_idx(source_indices)
else:
    idx = int(np.random.choice(source_indices))
```
Triggers when the active scenario's source-index pool has **fewer than 50 rows** (in practice:
`infiltration` — 7 test rows, and `heartbleed` — 2 test rows; no other scenario's mapped class
union falls below 50). Behaviour: the full index pool is shuffled once (`np.random.shuffle`),
then indices are served sequentially via a cursor; when the cursor reaches the end, the pool is
re-shuffled and the cursor resets — guaranteeing even coverage of the tiny pool (no immediate
repeats) rather than pure random choice, which could otherwise re-pick the same 1-2 rows
back-to-back very frequently given only 2-7 total options.

### 12.4 Activity diagram — full simulation run (start request → WebSocket broadcast)

Sequential steps and decision points, traced directly from `main.py`'s `/api/simulate/start`
handler and `simulator.py`'s `SimulationEngine.start()`/`_runner()`:

1. Analyst submits scenario + rate (+ optional duration) → `POST /api/simulate/start`.
2. **Decision**: valid JWT? → No → `401 Unauthorized`. → Yes → continue.
3. **Decision**: `rate <= 0`? → Yes → `400` ("must be at least 1 packet per second"). → No → continue.
4. **Decision**: `rate > 500` (`MAX_SIMULATION_RATE`)? → Yes → `400`. → No → continue.
5. **Decision**: scenario ID known (in `SCENARIOS` or `LEGACY_SCENARIO_ALIASES`)? → No → `400`. → Yes → continue.
6. `simulator_engine.start()`: sets `is_running=True`, records `start_time`, spawns the background `_runner()` asyncio task.
7. HTTP response `{"status": "started", ...}` returns to the analyst immediately — the loop below runs independently, asynchronously, from this point on.
8. **Loop** (while `is_running`):
   a. **Decision**: `current_scenario == "mixed_attack"`? → Yes → per-draw, 20% chance pick from `benign_baseline` indices, 80% chance pick from `all_attack_indices`. → No → use the scenario's static index pool.
   b. **Decision**: pool size < 50 (rare class)? → Yes → shuffled round-robin cursor (Section 8.4). → No → `np.random.choice`.
   c. Selected row's scaled features inverse-transformed back to raw values.
   d. `CascadeDetector.detect()` runs: **Decision**: Tier 1 (LightGBM) confidence ≥ 0.85? → Yes → verdict resolved at Tier 1. → No → **Decision**: Tier 2 (Random Forest) confidence ≥ 0.85? → Yes → resolved at Tier 2. → No → Tier 3 weighted vote → resolved at Tier 3.
   e. Synthetic IP/port metadata generated from the resulting `predicted_label` (Section 8.3), attached to the result.
   f. **Decision**: `predicted_label != "BENIGN"`? → Yes → persist an `Alert` row to SQLite. → No → skip persistence.
   g. `broadcast_detection(result)` → every connected `/ws/live` client receives the `"detection"` JSON event.
   h. In-memory telemetry counters updated (`packets_sent`, `attacks_detected`, `tier_breakdown`).
   i. **Decision**: `duration_seconds` set AND elapsed ≥ `duration_seconds`? → Yes → `is_running=False`, loop breaks. → No → `asyncio.sleep(1/rate)`, loop continues from (a).
9. Loop exits either via step 8i (duration reached) or via an explicit `POST /api/simulate/stop` (sets `is_running=False` and cancels the asyncio task) or an unhandled exception (caught, logged, `finally: self.is_running = False`).
10. Dashboard's Live tab, subscribed to `/ws/live`, updates the feed/gauge/attack-map/counters in real time as each `"detection"` event arrives (independent of the backend loop — purely reactive to WS messages).

### 12.6 State diagram — simulation session

States (from `SimulationEngine.is_running` and related fields):
- **Idle**: `is_running = False`, `current_scenario = None` (initial state; also the state after a stop, natural completion, or error).
- **Running**: `is_running = True`, `current_scenario` set, background `_runner()` asyncio task active, telemetry counters incrementing.

- `Running --[unhandled exception in _runner()]--> Idle` — caught by the `try/except/finally` in `_runner()`, which unconditionally sets `self.is_running = False` in `finally`.

## SECTION 14 — Anything I have missed

Not asked about directly, but worth describing in a report — with the relevant comments quoted verbatim.

**1. Memory-mapped test-split loading, not a full in-RAM load.** Both `CascadeDetector`
(computing benign averages) and `SimulationEngine` load the large cached `processed_data.npz`
file with `np.load(npz_path, mmap_mode="r")` (`backend/app/ml/cascade.py` line 80,
`backend/app/simulator/simulator.py` line 134) rather than a plain `np.load()`. This memory-maps
the array from disk instead of copying the full 2.45M/565K-row arrays into RAM on process
startup — a real, deliberate performance/footprint decision worth naming in a systems-design
section of the report.

**2. Frontend race-condition fix for stale AI chat responses.** `frontend/src/pages/Dashboard.tsx`
implements a generation-counter pattern (`chatGenerationRef`) so that if a user switches
conversation context (new chat, load a different saved thread, toggle incognito) while a Gemini
response is still in flight, the stale response is silently discarded instead of rendering into
the now-wrong conversation view. `generationAtSend = chatGenerationRef.current` is captured at
send time; the ref is incremented on every context switch; the response handler compares
`chatGenerationRef.current !== generationAtSend` before applying the result. This is a genuine
async-UI correctness bug class (not hypothetical) and its fix is a legitimate engineering
talking point.

**3. JWT revocation is intentionally in-memory, not persisted.** `backend/app/auth/crypto.py`:
```python
# In-memory revoked-token set (by jti). Session-scoped like the other singletons in
# this codebase (CascadeDetector, ConnectionManager) -- resets on server restart,
# which is an acceptable tradeoff for a locally-run FYP demo rather than standing up
# a persistent revocation store for a single-process deployment.
_revoked_jtis: set[str] = set()
```
This means logging out only invalidates a token for as long as the backend process stays up —
a restart silently un-revokes every previously-logged-out token. This is documented as a
deliberate, scoped-to-context trade-off, not an oversight, and is worth naming explicitly as a
"known limitation, not a bug" in a report's limitations section.

**4. `JWT_SECRET` fails safe rather than falling back to a hardcoded string** (already covered
in Section 7, but worth re-emphasizing as a security-decision talking point): if `.env` doesn't
set `JWT_SECRET`, `backend/app/config.py` generates a **random** `secrets.token_hex(32)` per
process rather than using a static fallback string — trading session persistence-across-restarts
for the guarantee that nobody can forge tokens by reading the source code of a misconfigured
deployment.

**5. Two redundant CIC-IDS2017 packagings on disk, handled defensively.** `data/raw/` contains
both `GeneratedLabelledFlows/` and `MachineLearningCSV/` (documented, overlapping repackagings
of the same underlying flows with different column sets). `find_csv_files()` in
`backend/app/data/loader.py` detects this and explicitly picks only one group (by directory,
preferring the larger file count) rather than silently concatenating both — the comment
explains why: mismatched schemas between the two packagings would inject NaN columns via
`pd.concat` and crash the downstream `RandomForestClassifier` feature-selection step. Verified
firsthand during this data-extraction pass (Section 2.1's own script run hit this exact code
path and logged the skip).

**6. LightGBM hyperparameters were empirically tuned after a real training failure**, not
chosen a priori (Section 3.1's quoted comment: default `num_leaves=31` combined with SMOTE's
synthetic clusters caused LightGBM to hit "no further splits with positive gain" and collapse
accuracy to 0.37–0.82 depending on subsampling; shrinking `num_leaves` to 15, raising
`min_child_samples` to 50, and adding `reg_lambda=1.0` fixed it, restoring ~0.997 accuracy).
This is a genuine, non-obvious debugging story worth a paragraph in a Results/Discussion
chapter — it demonstrates the SMOTE cap (item below) and model hyperparameters were not
independent decisions but were co-tuned against each other.

**7. The SMOTE oversampling cap (20,000/class) was also an empirical fix, not a default.**
Already quoted in full in Section 2.6 — fully balancing to the majority class
(`sampling_strategy="auto"`) was tried first and destabilized LightGBM specifically (via
~200,000x duplication of the 9-row Heartbleed class into near-identical synthetic points).

**8. WebSocket authentication uses a query-parameter token, not a header, and validates before
`accept()`.** `backend/app/main.py`'s `/ws/live` handler docstring: *"Browsers' native
WebSocket API can't set an Authorization header, so the JWT is passed as a query parameter
instead. Validated before accept() so an unauthenticated caller never receives a live
connection."* — a correct, deliberate handling of a real WebSocket-auth constraint (native
browser WebSocket clients cannot set custom headers on the handshake), not an accidental
weaker-auth path.

**9. Test suite failure (Section 11) is itself worth reporting as a finding, not hiding.** The
single failing test (`test_chat_rule_based_qa`) fails specifically *because* the AI Assistant's
Gemini integration is working correctly in this environment — a good example of a test's
assumptions drifting out of sync with a working feature, worth a one-line mention in a testing
chapter rather than pretending the suite is 100% green.

**10. No formal migration framework (e.g. Alembic).** Already noted in Section 6.3 — schema
evolution on the SQLite file is handled via hand-written, idempotent `PRAGMA table_info()` +
conditional `ALTER TABLE` statements in `init_db()`. Worth naming as a scope/tooling trade-off
appropriate for a single-database FYP demo, with "adopt Alembic" as a natural
production-hardening future-work item.
